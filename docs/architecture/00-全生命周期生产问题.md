### 一、 底层数据库与运行时环境问题

1. **Windows 平台异步事件循环与 `psycopg` 兼容崩溃**

   - **问题现象**：在 Windows 本地开发环境中运行 FastAPI + LangGraph 异步 PostgreSQL Checkpointer 时，底层报错崩溃（ProactorEventLoop 与 psycopg3 异步驱动不兼容）。

   - **解决方案**：在应用入口（`main.py`）及单测脚本最顶部强制注入平台防御判定代码：

     Python

     ```
     if sys.platform == "win32":
         asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
     ```

2. **连接池资源争抢与事务死锁风险**

   - **问题现象**：LangGraph Checkpointer 频繁写入二进制状态快照（`checkpoints` / `checkpoint_blobs`），与业务表（`ai_thread_mappings` 等）共用 SQLAlchemy 连接池时，极易引发事务阻塞或自动建表失败。
   - **解决方案**：实施**物理隔离双连接池架构**。在 `database.py` 中拆分为两个独立池：SQLAlchemy 异步池专门承载业务 CRUD 与 pgvector 检索；原生 `psycopg` 异步连接池（强制配置 `kwargs={"autocommit": True}`）专供 `AsyncPostgresSaver` 独占使用，并在 FastAPI `lifespan` 中统一托管建连、自动建表与连接释放。

3. **多审批人并发操作引发的状态机重复唤醒（并发击穿）**

   - **问题现象**：在 HITL（人机协同）挂起节点（`WAITING_HUMAN`），若多个调度员同时点击“核签通过”或前端弱网重复提交，会导致状态机被多次 `resume`，引发下游外部系统重复下发工单。
   - **解决方案**：引入**数据库级双保险**：
     - **CAS 乐观锁**：在 `ai_thread_mappings` 中增加 `lock_version` 字段，唤醒状态机前执行原子条件更新（`WHERE thread_id = :id AND lock_version = :v AND status = 'WAITING_HUMAN'`），更新影响行数为 0 则直接拦截。
     - **幂等防护键**：增加 `idempotency_key` 唯一索引，物理阻断前端高频连击。

### 二、 前后端联调、权限与渲染问题

1. **前端初始化请求业务接口被 403 权限拦截**
   - **问题现象**：普通申请人角色登录前端进入工作台时，页面默认拉取全量工单或待审批列表，触发后端角色校验，直接返回 `403 Forbidden` 报错。
   - **解决方案**：
     - **后端接口规范化**：严格执行基于 `creator_id` 和 `assigned_role` 的行级数据隔离与角色路由鉴权。
     - **前端 Tab 分流与按需请求**：重构前端工作台 Tab 状态，根据当前登录用户角色（申请人 vs 审批人）动态路由请求对应的接口（如“我发起的” vs “待我审批的”），避免越权预加载。
2. **传统长文本与富交互表单耦合、刷新丢失状态**
   - **问题现象**：大模型流式输出的审批意见和风险项混在纯文本中，前端页面刷新后无法还原交互按钮和印章状态；且遇到网络抖动重试时，前端丢失原始上下文参数。
   - **解决方案**：确立 **A2UI（Agent-to-UI）快照轨与动态卡片注册中心**：
     - 在 `ai_chat_messages` 表中独立设计 `kind`、`card_type`、`card_payload`（JSONB）和 `retry_payload`（JSONB）。
     - 前端建立动态卡片注册中心，刷新页面时直接读取 `card_payload` 渲染对应 Vue 组件（如对比卡、审批印章卡）；网络超时时直接携带自包含的 `retry_payload` 原地发起幂等重试，无需重新走全量推理。
3. **SSE 长连接流式传输代理超时断连**
   - **问题现象**：大模型深度思考（如安全规程多维推理）耗时较长，经过 Nginx 或负载均衡网关时，因超过 60 秒无数据帧传输被强制掐断连接。
   - **解决方案**：在 FastAPI 的 SSE 异步生成器中内置定时心跳保活机制（每隔 15 秒推送一次 `:ping\n\n` 空白注释帧），维持长连接活性。

### 三、 架构边界与可维护性问题

1. **AI 库与外部业务主系统强耦合（双写隐患）**
   - **问题现象**：初期容易把业务工单、设备台账等主数据直接建在 AI 数据库中，导致与外部 OMS/PMS 系统数据不同步。
   - **解决方案**：立下**资产边界法则**与 **ACL（业务防腐适配层）**。AI 库坚决不建全量业务主表，仅在 `ai_thread_mappings` 中保留 `biz_order_id` 弱引用（草稿阶段为 `NULL`，外部系统落库后再回填），所有主数据读写与状态回写全部收口至 ACL 适配层统一转发。
2. **检查点二进制 Blobs 膨胀与敏感数据合规风险**
   - **问题现象**：长期运行后 `checkpoint_blobs` 占用大量磁盘，且聊天记录可能明文留存手机号或专网敏感信息。
   - **解决方案**：补充**冷热归档 TTL（`is_archived`、`archived_at`）**，通过后台定时任务清理已完结超 30 天工单的底层二进制 Blobs；同时在消息入库管道增加脱敏过滤，写入后置 `is_sanitized = True` 供安全审计。
